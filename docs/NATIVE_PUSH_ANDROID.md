# Native Push: Android-Entwicklungsinstallation

Die Android-Dev-App hat die Kennung `at.floatbox.aesculapp.dev`. Das offizielle Capacitor-Plugin `@capacitor/push-notifications` ist installiert und synchronisiert. Die bisherige PWA nutzt weiterhin Web-Push; das Adminportal bleibt eine PWA. Solange Firebase und der native Serverversand fehlen, fordert die Android-App noch keine native Push-Freigabe an.

## Firebase-Projekt vorbereiten

1. Das bestehende Firebase-Projekt `aesculapp-dev` enthält derzeit zwei Android-App-Registrierungen: `at.floatbox.aesculapp.dev` und `at.stadtapotheke.trofaiach`. Die beiden App-IDs bleiben auch bei gemeinsamem Firebase-Projekt getrennt.
2. In Firebase eine Android-App mit exakt `at.floatbox.aesculapp.dev` registrieren. Für reinen FCM-Push werden weder Google Analytics noch eine SHA-Signatur benötigt.
3. `google-services.json` herunterladen und lokal unter `client/android/app/google-services.json` ablegen. Diese Datei ist in `client/android/.gitignore` ausgeschlossen. Sie gehört nicht in die Symfony-Konfiguration und nicht zum Apotheken-Deployment.
4. In den Firebase-Projekteinstellungen unter Cloud Messaging prüfen, dass die FCM HTTP v1 API nutzbar ist. Für den Versand vom Symfony-Server wird ein Service-Account mit Berechtigung zum FCM-Versand benötigt. Dessen private JSON-Datei nicht in Git und nicht in den Chat kopieren; sie wird separat in einem nicht öffentlichen Serverpfad bereitgestellt.

Auf dem Symfony-Server werden in der installationsspezifischen `.env.local` oder den Umgebungsvariablen `NATIVE_PUSH_ANDROID_APP_ID=at.floatbox.aesculapp.dev` und `FCM_SERVICE_ACCOUNT_FILE=/absoluter/privater/pfad/service-account.json` gesetzt. Für die Online-Installation gilt stattdessen die App-ID `at.stadtapotheke.trofaiach`. Beide können denselben Firebase-Projekt-Service-Account verwenden, aber jeder API-Server benötigt seine eigene private, unversionierte Kopie und die passende `NATIVE_PUSH_ANDROID_APP_ID`. Die Migration `Version20261008120000` legt die Gerätetabelle an. Erst nach Migration und beiden Konfigurationen wird die Aktivierung im Kundenprofil angeboten.

Wenn die lokale Windows-PHP-Installation keinen CA-Bundle konfiguriert hat, kann für den FCM-Transport zusätzlich `FCM_CA_FILE=G:/laragon/etc/ssl/cacert.pem` gesetzt werden. TLS-Prüfung bleibt aktiv; produktive Linux-Server verwenden normalerweise den systemweiten CA-Bundle.

Der Kunde erteilt die Gerätefreigabe ausdrücklich im Profil oder über den einmaligen Hinweis. Das FCM-Token wird verschlüsselt und mandantenbezogen gespeichert. Die bestehenden Push-Kategorien und die separate News-Einwilligung gelten auch für native Zustellung. An FCM gehen nur ein neutraler Titel, ein neutraler Hinweis und die Dashboard-Route; Termin-, Chat- und andere Inhaltsdetails lädt die App erst nach Anmeldung. Über „Push testen“ im Profil kann nach der Einrichtung eine echte Zustellung an die registrierten Geräte geprüft werden.

Die Firebase-Clientdatei allein aktiviert noch keine Zustellung. Ohne Server-Service-Account und Migration bleibt das native Push-Feature deaktiviert. Native iOS-Push-Zustellung ist noch nicht implementiert; die installierte iOS-PWA nutzt weiterhin Web-Push.

Die separate Online-Android-App liegt unter `client/android-apotheke` und wird mit `run-android-apotheke.ps1` gebaut. Sie verwendet die Firebase-Android-Registrierung `at.stadtapotheke.trofaiach`; ihre `google-services.json` liegt ausschließlich unter `client/android-apotheke/app/`. Die Datei kann mehrere `client`-Einträge desselben Firebase-Projekts enthalten, solange der passende Paketeintrag vorhanden ist. Standardmäßig wählt das Skript die Apotheken-API; für einen ausdrücklichen Demo-Test kann `-ApiTarget Floatbox` gesetzt werden. Auf dem jeweils gewählten API-Server `NATIVE_PUSH_ANDROID_APP_ID=at.stadtapotheke.trofaiach` und den zum Firebase-Projekt gehörenden Service-Account über `FCM_SERVICE_ACCOUNT_FILE` konfigurieren. Beide Dateien bleiben unversioniert. Vor einem Push-Test müssen Migration und Server-Code auf dem gewählten API-Server bereitstehen. Die Demo- und Apotheken-Datenbanken speichern Gerätetoken getrennt; bei einem Serverwechsel müssen Kunden ihre Geräte auf dem neuen Server erneut registrieren.
